# Error Handling Design Task

## Background

Kinglet bootstrap (C++) at HEAD has three error-handling features that need a unified design for the self-hosted compiler:

### Current State (C++ bootstrap)

1. **Cast**: `int(x) else fallback`
   - Syntax: `Type(value) [else fallback]`
   - Parser: `Parser::primary()` → `CastExpr(value, fallback)`
   - Checker: fallibility matrix (int↔float = infallible, string→num = fallible)
   - Compiler: `CastTo` opcode + Dup/IsNull/JmpFalse + Pop + fallback + Jmp over success path

2. **?? (Null Coalesce)**: `lhs ?? rhs`, `lhs ?? |e| rhs`
   - Syntax: between assignment and pipeline precedence
   - Parser: `Parser::coalesce()` → `NullCoalesceExpr(left, err_binding, right)`
   - Checker: LHS must be Result-shaped enum (Ok+Err variants), RHS must match Ok type
   - Compiler: Dup + EnumVariant test + JmpFalse → Err path (bind err to local or pop) + compile rhs + Jmp → Ok path (EnumPayloadGet)

3. **try**: `try expr`
   - Syntax: soft keyword at unary precedence
   - Parser: `Parser::unary()` → `TryExpr(value)`
   - Checker: operand must be Result-shaped. Ok→T, Err→early-return from fn (fn must return Result<_, E>)
   - Compiler: temp slot + StoreLocal + Pop, LoadLocal + EnumVariant + Eq + JmpFalse → Err path (LoadLocal + Return), Ok path (LoadLocal + EnumPayloadGet)

### Problem

`else` is confusing because it conflicts with conditional `if/else`. The user explicitly chose `??` as the unified syntax for fallback handling.

## Design Questions

Answer ALL of the following:

### Q1: Cast syntax change

Should Cast `else` be replaced with `??`?

- Option A: `int(x) ?? 0` — Cast always uses `??`, `else` is removed
- Option B: Both `else` and `??` are accepted (backward compat, deprecated `else`)
- Option C: Keep `else` for Cast, `??` is only for Result types

Which? Why?

### Q2: CastResult type

Current Cast produces null on failure (no type info). Should we:

- Option A: Keep null — CastTo pushes null, caller uses `??` (or `else`) to provide fallback. Infailable casts are always safe.
- Option B: Cast produces a Result<T, CastError> — then `??` and `try` work naturally with it
- Option C: Make a distinction — infallible casts produce T directly, fallible casts require `??` fallback inline (not Result-wrapped)

Which? Why?

### Q3: try and Cast interaction

If Cast uses `??` syntax for fallback, should `try int("42")` work?

- Option A: No — Cast doesn't produce a Result type (Option A from Q2), so `try` can't work with it
- Option B: Yes — Cast could be Result-wrapped optionally (e.g., `int?(x)` produces `Result<int, CastError>`, then `try int?(x)` works)

Which? Why?
